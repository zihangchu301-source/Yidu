## 一、先搞清楚：Supabase 是什么

Supabase 官方给自己的定位是「开源的 Firebase 替代品」。翻译成人话：

> 别人已经写好了一整套后台服务，你只管调用。

它一次性提供了三样东西：

| 组件 | 干什么 | 类比 |
|---|---|---|
| GoTrue（账号系统） | 注册、登录、发登录凭证 | 门卫 |
| PostgREST（数据接口） | 把数据库的表自动变成 HTTP 接口 | 前台 |
| PostgreSQL（数据库） | 真正存数据的地方 | 仓库 |

没有它的话，要自己租服务器、装数据库、写登录逻辑、写一堆接口，通常要两三天。有了它，填两个参数就能用。

**关键点：Supabase 只是一个软件套件，谁装都行。** 官方装在新加坡，阿里云把它装在杭州。

## 二、我们用的是阿里云的哪一款

阿里云没有叫「Supabase」的独立产品，它藏在下面这个路径里：

```
阿里云控制台
└── 云原生数据仓库 AnalyticDB PostgreSQL 版（产品代号 ADB PG）
    └── 左侧导航 → AgenticDB → Supabase
```

### 为什么不用官方 Supabase

| | 官方 Supabase | 阿里云 AnalyticDB 版 |
|---|---|---|
| 机房 | 新加坡 | 杭州 |
| 国内访问延迟 | 200–500 ms，经常超时 | 20–40 ms，稳定 |
| 免费版闲置策略 | **7 天没请求就暂停项目** | 无此策略 |
| 计费 | 美元信用卡 | 人民币，有免费规格 |
| 接口 / SQL 写法 | 完全一样 | 完全一样 |

代码里 `[cloud] supabase_url` 填哪家的地址都能跑，因为协议是同一套。

### 实际开了三个资源

| 资源 | 名字 | 规格 | 作用 | 花钱吗 |
|---|---|---|---|---|
| 专有网络 VPC | `yidu-vpc` | 172.16.0.0/16 | 一个隔离的私有网段 | 免费 |
| 交换机 vSwitch | `yidu-switch` | 172.16.0.0/24（杭州可用区J） | VPC 内划出的子网 | 免费 |
| Supabase 实例 | `yidu` | 1核2G | 跑着上面那三件套 | 免费规格，0 元 |

**为什么必须先建 VPC**：创建实例时「专有网络」和「交换机」是必填项，没有就选不了。这两个东西本身不产生费用，只是容器。

## 三、数据库里到底存了什么

### 4.1 业务表 `yidu_records`

整本书库、进度、笔记、查词全部塞在这一张表里（键值对设计，加新功能不用改表结构）：

| 栏位 | 类型 | 说明 |
|---|---|---|
| `id` | bigserial | 自增主键 |
| `user_id` | uuid | 属于哪个账号，外键指向 `auth.users` |
| `kind` | text | 五选一：`book` / `progress` / `annotation` / `dict` / `setting` |
| `key` | text | 这条记录的标识：书的哈希、笔记的 uid、词条的单词… |
| `payload` | jsonb | 真正的内容，结构随 kind 变 |
| `deleted` | bool | 软删除标记（一台设备删了，另一台也要跟着删） |
| `updated_at` | timestamptz | 最后修改时间，冲突时靠它判断谁更新 |

`kind` 各自的 payload：

| kind | key | payload 里有什么 |
|---|---|---|
| `book` | 书的 SHA1 哈希 | 书名、作者、章数、段数、语种、加入时间、**各设备的阅读时长** |
| `progress` | 书的哈希 | 读到第几章、第几段、百分比 |
| `annotation` | 笔记 uid | 书、章、段、类型（划线/笔记/书签）、原文、批注、字符区间 |
| `dict` | 单词 | 单词、查到的时间、来源书/章/段 |
| `setting` | 偏好名 | 字号、主题、行高等（**`device_id` 被排除，不参与同步**） |

### 4.2 Supabase 自带的表

- `auth.users` —— 账号，只存邮箱和**哈希后的**密码。明文密码谁都看不到，包括管理员。
- `auth.identities` / `auth.sessions` / `auth.refresh_tokens` —— 登录态，由 GoTrue 自己维护。

### 4.3 行级安全（RLS）—— 隐私的关键

表上启用了 RLS，配了 4 条策略（`docs/supabase_schema.sql`）：

```sql
-- 每个人只能看到、改到、删掉自己的行
using (auth.uid() = user_id)
```

这意味着：**就算 anon key 被别人拿到，他查出来也永远是空数组**，因为请求里没有你的登录令牌，`auth.uid()` 是 null。这是 Supabase 的安全基石，不是靠"藏 key"来保密的。

## 四、数据怎么流动

```
用户点「立即同步」
   ↓
本地 Flask（source/cloud.py 的 SyncEngine）
   ↓ 1. 先拉：GET /rest/v1/yidu_records?updated_at=gt.<上次同步时间>
   ↓ 2. 比对：本地改过？云端改过？谁的时间新算谁的
   ↓ 3. 再推：POST /rest/v1/yidu_records（带 on_conflict=user_id,kind,key）
   ↓
阿里云杭州机房 → Kong 网关（校验 apikey）→ PostgREST → PostgreSQL
```

几个实现细节值得知道：

- **不做全量覆盖**：每条记录同步后会记一个内容指纹（`sync_meta` 表），指纹没变就不上传，省流量。
- **删除是软删除**：本地删一条，写一条墓碑记录传上去，另一台设备同步时才知道要删。
- **冲突按时间取新**：同一本书你在电脑改过、手机也改过，`updated_at` 新的那个赢。
- **阅读时长特殊**：按设备分别记账（`read_time_dev` 表），同设备取较大值、跨设备求和，避免重复累加。

## 五、日常操作：控制台怎么用

### 5.1 进控制台

```
https://gpdbnext.console.aliyun.com/gpdb/cn-hangzhou/supabase
```

进去能看到项目列表，一行就是我们的 `yidu` 项目。**账号密码见本地凭据文件。**

### 5.2 你可能会用到的操作

| 想做什么 | 怎么做 |
|---|---|
| 看项目是否正常 | 控制台 → 项目列表 → 「状态」列显示 `运行中` |
| 改 IP 白名单 | 项目行 → 「修改白名单」（现在是 `0.0.0.0/0`，全放开） |
| 重置数据库密码 | 项目行 → 「重置数据库密码」——**改了要同步改凭据文件** |
| 看用量 | 控制台首页 → 费用中心 → 资源使用 |
| 暂停 / 删除项目 | 项目行 → 更多操作。**删了就没了，先备份** |

### 5.3 管理界面（Studio）长什么样

打开 `https://<项目ID>.supabase.opentrust.net` 就是 Supabase 官方那个 Studio（网页后台），
阿里云只是把它装在杭州。**界面是纯英文的，没有中文版，也没有内置翻译。**

左侧一列图标从上到下（把鼠标停上去会显示英文名）：

| 图标位置 | 英文名 | 干什么 | 你会用吗 |
|---|---|---|---|
| 1 | Project overview | 项目概览 | 看看就行 |
| 2 | Table Editor | 像 Excel 一样看/改表 | 偶尔看数据用 |
| 3 | SQL Editor | 写 SQL、跑脚本 | 重建表时用 |
| 4 | Database | 备份、扩展、角色 | 基本不用 |
| 5 | Authentication → Users | **看有哪些账号注册了** | 有时用 |
| 6 | Storage | 上传文件（我们没用） | 不用 |
| 7 | Edge Functions | 云函数（我们没用） | 不用 |
| 8 | Realtime | 实时推送 | 不用 |
| 9 | Advisors | 安全检查建议 | 不用 |
| 10 | Logs | 请求日志 | 排错时看 |
| 11 | API Docs | 接口文档 | 不用 |
| 12 | Integrations | 第三方集成 | 不用 |
| 13 | **Project Settings** | 项目设置 | 会用到 |

`Project Settings → API Keys` 这一页就是取 key 的地方：

- `anon` / `public` —— 就是客户端要用的那把，右边有 `Copy`。**这个可以给别人**
- `service_role` —— 要点 `Reveal` 才显示。**这个绝对不能给任何人**

### 5.4 ⚠️ 界面上的坑（以及别乱点的地方）

**已知问题**：`API Keys` 这一页偶尔会一直转圈（我遇到过，此时它调用的接口返回 404），
刷新或者重新进一次一般就好了。**如果界面卡住拿不到 key，用下面的 curl 兜底**：

```bash
# 拿项目设置（里面有 jwt_secret 和两个 api key 的明文）
curl -u "<项目ID>:<Dashboard密码>" \
  https://<项目ID>.supabase.opentrust.net/api/platform/projects/default/settings

# 直接跑 SQL（等同于 SQL Editor）
curl -u "<项目ID>:<Dashboard密码>" -H "Content-Type: application/json" \
  -d '{"query":"select count(*) from yidu_records"}' \
  https://<项目ID>.supabase.opentrust.net/api/platform/pg-meta/default/query
```

**这些东西点之前先想清楚，点错了数据就没了**：

| 位置 | 后果 |
|---|---|
| Project Settings → General → Delete project | 项目连同全部数据一起删除，**不可恢复** |
| Project Settings → Database → Reset database password | App 立刻登录不上，要改配置 |
| Authentication → 删除用户 | 该账号的同步数据全丢 |
| Table Editor 里手改/删除 `yidu_records` 的行 | 会破坏同步状态，可能被下次同步又"复活" |
| Database → Roles 里动 postgres 权限 | 可能让 App 整个连不上 |

**这个实例的一个已知弱点**：`jwt_secret` 是 Supabase 官方的演示默认值
（`super-secret-jwt-token-with-at-least-32-characters-long`），懂行的人理论上可以自己签发
任意用户的 JWT。对个人项目风险可接受（还得知道项目地址、猜用户 id），但如果哪天要放
敏感数据，务必先换 jwt_secret 并重新生成 key。

## 六、钱的问题

- 当前规格 **1核2G，免费**，不绑卡、不扣费。
- 存储 1 GB。现在 211 条记录约几十 KB，1 GB 能装几百万条。
- 不传 epub 文件，所以不吃存储——一本 30 MB 的书传十本就把额度用完了。
- **没有"闲置多久就删"的政策**（官方 Supabase 免费版是 7 天）。

## 七、安全模型：四把钥匙

| 钥匙 | 权限 | 泄露后果 | 能不能公开 |
|---|---|---|---|
| App 账号（邮箱+密码） | 只能读写自己的行 | 别人能看到你的阅读记录 | ❌ |
| **anon key** | 以"匿名用户"身份调用接口，受 RLS 约束 | 能注册垃圾账号；读不到别人的数据 | ⚠️ 设计上可公开 |
| **service_role key** | 绕过所有 RLS，等于数据库超级权限 | 全库数据可读可删 | ❌ 绝对不能 |
| 数据库密码 | 直连 5432 端口 | 同上 | ❌ 绝对不能 |
| Dashboard 密码 | 进 Studio 管理界面 | 能改表、改数据 | ❌ |

### 为什么 anon key 可以出现在客户端

网页/App 里必然有一把能调接口的 key，否则前端没法工作。Supabase 的做法是：这把 key 只代表
"匿名身份"，真正的权限边界画在数据库的 RLS 策略上。官方文档明确说 anon key 可以公开。

**本项目的实际情况**：`python_shims/yidu_android.py` 里预置了 anon key 和项目地址，
代码是公开仓库，所以**这两个值对全世界可见**。这是有意为之——不然手机用户装完 App
还得手抄 208 个字符，不现实。

已知的暴露面：
1. 别人知道项目地址，可以往 `/auth/v1/signup` 注册小号（邮箱验证是关的）。
2. 但他们读不到你的任何数据（RLS 挡着），也无法删除你的行。

如果真的介意，两件事可以收紧（但都需要改动，见下节）。

### 想收紧的话怎么做

| 目标 | 做法 |
|---|---|
| 不让陌生人注册 | 关掉 GoTrue 的 `GOTRUE_MAILER_AUTOCONFIRM` / 开 `DISABLE_SIGNUP`（需要能改环境变量，阿里云免费版没开放） |
| 不让 anon key 公开 | 从 `python_shims` 里删掉，改为构建时从 GitHub Secrets 注入（需要你在 GitHub 仓库 Settings → Secrets 里加一条） |
| 换掉默认 jwt_secret | 只能重建实例，或联系阿里云工单 |

目前**没做**，因为收益低（RLS 已经挡住了数据）而代价是会破坏"装完即用"。

## 八、出问题怎么查

### 8.1 客户端报错对照

| App 上的提示 | 真实原因 | 怎么办 |
|---|---|---|
| 连不上云端 | 网络不通 / 白名单拦了 | 检查白名单是否为 `0.0.0.0/0` |
| Invalid authentication credentials | anon key 不对 / 过期 | 重新取 key，更新 config.ini |
| 账号或密码不对 | 密码错，或账号没注册 | 先点「注册新账号」 |
| 这本书的正文还没下载到本机 | 书目同步过来了，epub 文件没跟过来 | 重新导入同一个 epub（会保留笔记） |
| 同步完成：下载 0 条，上传 0 条 | 正常，两边已经一致 | 不用管 |

### 8.2 直接查云端

```bash
# 看这个用户有多少条数据
curl -u "<项目ID>:<Dashboard密码>" -H "Content-Type: application/json" \
  -d '{"query":"select kind, count(*) from yidu_records group by kind"}' \
  https://<项目ID>.supabase.opentrust.net/api/platform/pg-meta/default/query

# 看有哪些账号
  -d '{"query":"select email, created_at, last_sign_in_at from auth.users"}'

# 清理测试账号（连同它的数据）
  -d '{"query":"delete from yidu_records where user_id = (select id from auth.users where email='\''x@y.z'\''); delete from auth.users where email='\''x@y.z'\'';"}'
```

### 8.3 代码在哪

| 文件 | 职责 |
|---|---|
| `source/cloud.py` | `SyncEngine`：注册/登录/登出、拉取、比对、推送、冲突处理 |
| `source/config.py` | `[cloud]` 段读写（`save_cloud_settings`） |
| `source/server.py` | `/api/cloud/*` 六个接口 + 导入修补逻辑 |
| `source/state_manager.py` | `sync_source()`（本地→扁平记录）、`apply_remote()`（云端→本地） |
| `docs/supabase_schema.sql` | 建表 + RLS 策略，重装时直接跑 |
| `python_shims/yidu_android.py` | 安卓端预置地址/密钥、老配置自动补齐 |

## 九、如果要从零重建

1. 阿里云 → AnalyticDB PostgreSQL → Supabase → 创建项目（免费测试创建，1核2G，杭州，白名单选"是"）
2. 拿到项目 ID 和 Dashboard 密码
3. 用第五节的两条 curl 取出 `anon key`
4. 把 `docs/supabase_schema.sql` 全文 POST 到 `/api/platform/pg-meta/default/query`
5. 把地址和 anon key 填进 `config.ini` 的 `[cloud]`，或写进 `python_shims/yidu_android.py` 的 `_CLOUD_URL` / `_CLOUD_ANON_KEY`
6. App 里注册账号 → 首次同步把本地数据推上去

## 十、一句话总结

> 数据存在杭州的一个 PostgreSQL 数据库的一张表里；阿里云负责跑机器，Supabase 负责提供登录和读写接口；
> 权限靠数据库的行级策略（RLS）保证，不是靠藏 key；客户端那把 anon key 天生就是公开的。
